# Agent Review Studio operator guide

This guide teaches the review workflow before asking you to score an agent. It follows the same order as the in-product guided tour.

## What you are doing

You are evaluating a **run**: one versioned attempt by an agent or harness to complete one versioned test case. You are not editing the source and you are not training model weights during the review.

The Studio combines three kinds of evidence:

- **Imported or generated artifacts:** the run, source card, claim candidates, evidence excerpts, proposed actions, memory candidates, uncertainty labels and execution trace.
- **Automated evaluator results:** deterministic checks for structure, provenance, relevance, context, action specificity and trace completeness.
- **Human judgment:** categorical claim labels, corrections, five product-quality scores and a final decision.

Claims are generated by the selected runner or imported from an external run bundle. In the built-in deterministic runner, the source is normalised into stable lines, metadata is excluded, substantive statements are ranked, and each candidate retains its source line. These are **claim candidates**, not verified truths.

## The operator flow

### 1. Choose the scope

Open the **Workspace** menu in the top bar to switch agents or harnesses. Every custom workspace has a plainly labelled **Delete** action in that same menu; it opens the exact-name confirmation before anything is removed. The menu also creates a new workspace and links to archived workspaces. The sidebar **plus** button offers the same creation flow and asks for four things: workspace name, agent/harness name, the outcome you are building toward and the primary evaluation goal. A workspace contains datasets, harness versions, sessions, runs and review history.

The sidebar is a **workspace stack**. Select a workspace row to expand it; opening another workspace collapses the previous one. Inside the expanded row, choose **Pages** to navigate that workspace's tools or **Runs** to see only its dated sessions and immutable runs. Each workspace remembers whether you last used Pages or Runs.

Use a workspace's three-dot menu—or right-click its row—to rename it, edit its identity, archive it or begin guarded deletion. Permanent deletion always requires typing the exact workspace name. Settings also archives the current local workspace and restores archived workspaces. The built-in Chaser Agent example can be renamed but cannot be archived or deleted.

On desktop, drag the thin rail at the sidebar's right edge to resize it, double-click the rail to reset it, or use its arrow keys when focused. **Minimise sidebar** reduces the stack to accessible labelled workspace icons. At tablet and phone widths, **Browse** opens the complete scrollable drawer and keeps the next workspace row visible below a capped inner panel. Use the information button labelled **Help & tour** in the header—or **Start guided onboarding** in Settings—to restart the 19-scene walkthrough.

On Overview, select an evaluation session and open the next run in the queue. The built-in Chaser Agent example opens the corrected candidate first. The legacy run remains available as a baseline showing the metadata-leakage and relevance failures the evaluator should catch.

### 2. Understand the task

Read the goal, workflow profile, source card, original source and privacy class. Confirm that the evaluation target matches the task you intend to judge. A local source line proves where text came from inside the retained artifact; a primary-source URL identifies its online origin when one was supplied.

### 3. Verify each claim candidate

For every claim:

1. read the agent output;
2. read the exact evidence and surrounding context;
3. open the retained source or primary URL when needed;
4. inspect linked actions and trace steps;
5. use **Next: label this candidate** to reach the judgment controls;
6. apply one or more categorical labels;
7. write a correction when the chosen failure label requires one.

Use **Supported and relevant** only when the candidate is both supported by the cited evidence and useful for the task. Other labels separate distinct failure modes such as metadata mistaken for a claim, irrelevant content, missing context, unsupported content, misclassification, duplication, external-verification needs or an unrelated linked action.

### 4. Confirm the remaining artifacts

Review actions, memory candidates, uncertainty labels and the full execution trace. These confirmations prove that the review covered the whole run rather than only the most visible claim.

### 5. Score the run once

Score five product-quality dimensions from 0 to 3 after the claim-level review is complete. Use the rubric links for dimension-specific anchors. These scores describe the run as a whole; they are not repeated for every claim.

Choose a final decision:

- **Pass:** suitable for the intended use and regression set.
- **Needs revision:** useful direction, but a correction is required before acceptance.
- **Fail:** material correctness, relevance, safety or evidence problems.

### 6. Preserve the result

Finishing creates an immutable review revision. A later re-review creates another linked revision. Drafts can change; finished revisions do not. Export the evaluation pack to hand evidence to engineers or another governed system.

### 7. Improve and re-test

Use reviewed failures to update prompts, retrieval, tools, approval rules, memory policy or orchestration. Create a new harness/configuration version, rerun the same immutable test case, compare candidate against baseline, and inspect aggregate failures and the CI gate.

## Learn before configuring evaluators

Open **Learn** for the searchable Agent Harness Field Guide. The strategy builder uses the workspace goal and description to recommend three deliberately separate layers:

- deterministic rules for repeatable schema, provenance, threshold and state checks;
- probabilistic or model-graded evaluators for semantic quality that rules cannot express;
- human authority for ambiguous, high-impact or product-quality decisions.

The Python example is a starter template only. It does not execute in the browser. A future Python or model-grader service must be connected, versioned and recorded before the Studio can claim that evaluator ran.

## Training boundary

Agent Review Studio can produce reviewed examples suitable for **training-data selection**, but it is not a trainer. A separate model-training pipeline must approve the dataset, define desired target outputs, configure the model and compute, execute the training job, version the resulting model and run this evaluation suite again.

That gives the durable engineering loop:

`versioned test case -> versioned harness -> immutable run -> automated checks -> human review -> correction -> candidate revision -> baseline comparison -> regression gate`

## Your first Chaser Agent review

Start with **Relevance Regression Candidate - 1 Sep 2026 / Candidate 1**. The first claim should be a substantive Cloudflare Monetization Gateway statement, not a document-status line. Check that it retains surrounding context, its source line and a specific linked action. Review all claim candidates before entering the five run-level scores.
